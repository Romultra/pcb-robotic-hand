# Motor Driver — 5× Servo

The design uses **direct ESP32 PWM through a level shifter** rather than a
dedicated servo-driver IC (e.g. PCA9685). The ESP32-S3's LEDC peripheral can
trivially generate five independent 50 Hz PWM channels with 1 µs resolution,
which is plenty for hobby-servo 1–2 ms pulse widths.

## Path

```
ESP32 GPIO --(3.3 V PWM)--> TXS0108E (U6) --(5 V PWM)--> 220 Ω --> servo header SIG pin
                                                        (R13–R17)    (H1–H5)
```

- **TXS0108E (U6)** — 8-channel bidirectional level shifter (TSSOP-20). Five
  channels used. A-side powered from 3.3 V, B-side from 5 V.
- **R13–R17 (220 Ω)** — series protection on each shifted output before it
  leaves the board.
- **Headers H1–H5** — 3-pin 2.54 mm, pinout `[SIG, +5V, GND]` (pin 1 = signal,
  pin 2 = 5 V-SERVO, pin 3 = GND).

The five ESP32 pins involved are GPIO4, 5, 6, 7, and 15. TXS0108E OE is
hard-tied on the PCB — firmware doesn't drive it.

## Servo power rail (the interesting design choice)

The +5 V going to the servos is **a separate switched rail** (`5V-SERVO`),
generated by its own TPS56637 buck (U4). The buck's EN pin is wired to **ESP32
GPIO8 (SERVO_EN)**, so firmware can completely cut servo power when the hand is
idle. This is the single largest power-saving lever on the board.

There's also a visual feedback channel: LED6 (green) is wired from 5V-SERVO
through a 1.2 kΩ current-limit resistor, so the developer can see at a glance
whether the rail is on.

## ESD / signal protection

D1–D3 (LESD5D5.0CT bidirectional TVS) sit on the USB-facing nets, not the
servo lines. The servo signals rely on the 220 Ω series resistors as primary
mis-wiring protection.

## Not implemented

- No current sensing on the servo rail. Power monitoring (e.g. shunt + INA
  later) would need a future revision.
- No per-servo enable. Either all servos are powered, or none.

## Calibration & soft limits (firmware)

Once the servos drive the real fingers through the tendon strings, two things can
break the hand: a servo's usable range may be under 180°, and pulling past a
finger's mechanical end over-tensions the string. The firmware (not the webapp)
enforces the protection, so every command path is covered.

These are absolute-position servos, so a given command always reaches the same
physical angle: no homing is needed, and the stored values stay valid across
power cycles as long as the ropes aren't repositioned.

- Each channel stores `open_cmd`, `closed_cmd` and `home_cmd` (servo commands at
  the safe fully-open / fully-closed / park poses) plus a `valid` flag in **NVS**
  (`Preferences`). Storing open/closed rather than min/max also records the
  linkage direction, so inverted fingers need no special case.
- `servos::set_angle` (raw) clamps to the `[open,closed]` band; `set_finger`
  remaps a normalized 0..180 finger value (from hand-tracking) into the band.
  Both clamp, so sliders, `SERVO_FRAME`, playback and live-mirror all stay inside
  each finger's safe travel.
- **No move on boot:** `init()` attaches the channels but writes nothing (the
  rail is off anyway, so a reset mid-motion can't jerk a rope). A "move to open"
  action ramps gently to `home_cmd` for parking; `set_power(true)` parks
  calibrated channels at the open end before energising.
- A **calibration mode** relaxes the band so each finger can be jogged (in
  firmware-capped steps) to find its real travel, then captured. Driven over the
  `SERVO_CAL` BLE characteristic (`000d`) from the webapp's Finger Calibration
  panel, which shows a live angle and the motor range seen while jogging.

See `journal/decisions/004-servo-finger-calibration-safety-limits.md`.

## Reference: TowerPro MG995 servo

The five servos are TowerPro MG995 (analog hobby servo, metal gears, JR-type
3-pin connector). Specs below underpin the 5V-SERVO rail sizing and the PWM
timing in firmware.

### Electrical

| Parameter | Value |
|-----------|-------|
| Operating voltage | 4.8 – 6.6 V (some sources list up to 7.2 V) |
| Idle current (holding position) | ~10 mA |
| No-load running current | ~170 mA |
| Stall current | ~1200 mA (1.2 A) at 6 V |

### Performance

| Parameter | At 4.8 V | At 6.0 V |
|-----------|----------|----------|
| Stall torque | 9.4 kg·cm | 11.0 kg·cm |
| Speed | 0.20 s / 60° | 0.16 s / 60° |

### Control signal

| Parameter | Value |
|-----------|-------|
| Frame rate | 50 Hz (20 ms period) |
| Pulse width range | 0.5 ms (0°) – 2.5 ms (180°); centre 1.5 ms |
| Dead band | ~5 µs (components101) / 1 µs (TowerPro page) — sources disagree |
| Rotation range | 180° |

### 5-servo power budget

| Scenario | Per servo | 5 servos total |
|----------|-----------|----------------|
| All idle | 10 mA | 50 mA |
| All running, no load | 170 mA | 850 mA |
| All stall (worst case) | 1200 mA | 6 A |

The 5V-SERVO buck (TPS56637, 6 A continuous) covers the absolute worst case
with no headroom margin — fine in practice since simultaneous stall on all five
fingers is not an operating condition.

Note: MG995 is discontinued by TowerPro. The MG996R is the drop-in successor
(stall ~2.5 A at 6 V, tighter dead band). If a future revision switches to
MG996R, the rail-current numbers would need re-checking.

Sources:
- [TowerPro MG995 page](https://towerpro.com.tw/product/mg995-robot-servo-180-rotation/)
- [MG995 datasheet (electronicoscaldas)](https://www.electronicoscaldas.com/datasheet/MG995_Tower-Pro.pdf)
- [ServoDatabase MG995](https://servodatabase.com/servo/towerpro/mg995)

## Reference: ESP32-S3 LEDC PWM for servo control

LEDC is the ESP32-S3's general-purpose PWM peripheral and is what generates
the 50 Hz servo pulses. Key parameters:

| Parameter | Value |
|-----------|-------|
| Channels | 8 (low-speed mode only on S3) |
| Max timer resolution | 14 bits (SOC_LEDC_TIMER_BIT_WIDTH = 14) |
| Clock sources | APB_CLK (80 MHz), XTAL_CLK (40 MHz), RC_FAST_CLK (~20 MHz) — all timers share one source |
| Timers | 4 (5 servos at the same 50 Hz can share a single timer) |

At 14 bits / 50 Hz, the duty values for the servo pulse range are:

- 0.5 ms (0°): duty = 0.5/20 × 16384 ≈ **410**
- 1.5 ms (90°): duty ≈ **1229**
- 2.5 ms (180°): duty ≈ **2048**
- Angular resolution: (2048 − 410) / 180 ≈ **9.1 steps per degree** — far finer than the MG995's mechanical resolution.

Quirks:
- At max resolution, duty cannot be set to exactly 2^14 due to a hardware bug; this is harmless for servo use (we never hit 100 % duty).
- Channels on the same timer share frequency and resolution.
- `ledc_find_suitable_duty_resolution()` is a helper for runtime checks.

Source: [ESP-IDF LEDC docs (ESP32-S3)](https://docs.espressif.com/projects/esp-idf/en/stable/esp32s3/api-reference/peripherals/ledc.html).

## Why direct LEDC instead of a PCA9685

Early in the design phase the obvious alternative was an NXP PCA9685 — a 16-ch
I²C PWM driver popular in hobby robotics. The comparison:

| Factor | ESP32-S3 LEDC (chosen) | PCA9685 |
|--------|------------------------|---------|
| Channels available | 8 (need 5) | 16 (need 5) |
| Resolution | 14-bit (16384) | 12-bit (4096) |
| GPIO cost | 5 pins (one per servo) | 2 pins (I²C) |
| Extra hardware | None | PCA9685 IC + passives |
| Output logic level | 3.3 V (needs the TXS0108E shift) | 5 V native |
| Update path | Direct register write | I²C transaction |
| BOM cost | Free (built-in) | ~$1–2 + supporting parts |

The ESP32-S3 has plenty of free GPIO and three spare LEDC channels left over
after the five servos, so the PCA9685's GPIO-saving advantage is moot.
Direct LEDC is simpler, higher-resolution, and lower-BOM. The TXS0108E
handles the 3.3 → 5 V logic translation that the PCA9685 would have given for
free.

Source: [NXP PCA9685 datasheet](https://www.nxp.com/docs/en/data-sheet/PCA9685.pdf).
